# Agent Academy — 제작·분업 계획

버전 0.2 · 2026-11-09 · A 총괄 / B~F 병렬 제작

제품 기준은 [PRODUCT_SPEC.md](PRODUCT_SPEC.md), 모든 봇의 공통 규칙은 [../AGENTS.md](../AGENTS.md)다. 이 문서는 제작 방법이다. 아래 설계 선택과 역할 배치는 사용자 원안과 구분한다. 사용자는 각 봇에 파일·명령을 직접 전달한다.

## 1. 실행 순서

1. **A부터 시작한다.** 저장소·Codespaces 상태를 확인하고 공통 기반·타입·진입점을 준비한다.
2. A가 실행 가능한 기반 커밋과 역할별 worktree를 만든 뒤 `A_READY`를 보고한다.
3. 사용자가 B~F를 각 지정 worktree에서 시작시킨다. B~E는 기능 개발, F는 검증 준비와 완료된 부분 리뷰를 진행한다.
4. 각 봇은 자기 변경과 인계 문서를 커밋하고 사용자에게 결과를 보고한다. 사용자가 A에게 수합을 지시한다.
5. A는 결과를 순차 통합하고 F는 정확한 통합 커밋을 대상으로 검증한다. 오류는 담당자에게 반환하거나 해당 작업자가 멈춘 뒤 A가 수정한다.

새 채팅창만 여러 개 열면 파일이 자동 분리되는 것은 아니다. 별도 worktree와 브랜치가 필요하다. 다른 세션의 자동 실행·자동 통신은 전제하지 않는다.

## 2. 최초 기술 선택

다음은 **DESIGN_DRAFT**다. 기존 Codespaces에 구현이 있으면 먼저 읽고 유용한 구조를 유지한다. 기존 구현이 없으면 A가 아래 출발안을 현재 환경에 맞게 채택하거나 짧은 근거와 함께 변경할 수 있다. 일반적인 제작 선택 때문에 사용자 응답을 기다리지 않는다.

| 영역 | 초기 제작안 | 이유와 한계 |
| --- | --- | --- |
| 웹 앱 | TypeScript + React + Next.js App Router | 화면과 서버 경계를 한 프로젝트에서 관리. 설치 버전·Node 조건은 공식 문서와 환경에서 확인 |
| 게임 공간 | Phaser 기반 2D 렌더링, 깊이감 있는 교실 표현 | 한 교실의 이동·충돌 구현에 집중. 실제 3D 엔진을 쓴다고 표현하지 않음 |
| 화면 구성 | DOM 기반 선택·상담 UI + 클라이언트 전용 게임 캔버스 | 입력 폼과 게임 입력을 분리. 서버 렌더링에서 게임 엔진을 실행하지 않음 |
| 디자인 | 따뜻한 팔레트, 일관된 테두리·그림자·질감·서체 | A가 토큰을 정하고 B~D가 공유. 픽셀아트/특정 렌더링 기법 자체는 사용자 확정이 아님 |
| 외부 호출 | 서버 측 어댑터 | 공급자 키를 브라우저에 노출하지 않고 오류·지원 상태를 정규화 |
| 저장 | 로컬 개발에서 지속되는 단순 저장 계층 | A가 환경에 맞춰 선택. 학습 작업·중복 요청 식별을 메모리 변수에만 두지 않음 |
| 모델 탐색 | Hugging Face 등 공식 소스 우선 | 공급처마다 접근·학습 지원이 다름. 가짜 통합 카탈로그를 만들지 않음 |
| 학습 연결 | 검증 가능한 공급자 한 경로부터 구현 | Nebius 우선 검토는 사용자 언급에 따른 출발점. 공급자 확정·전체 모델 지원을 의미하지 않음 |

기술 검토 출발점: [Next.js 설치](https://nextjs.org/docs/app/getting-started/installation), [Phaser 소개](https://docs.phaser.io/phaser/getting-started/what-is-phaser), [Claude Code worktrees](https://code.claude.com/docs/en/worktrees). 2026-11-09 공식 문서 확인. 이 링크는 현재 Codespaces에서의 설치·실행 증거가 아니다.

## 3. A가 먼저 만드는 공통 기반

### A-0. 환경과 기존 작업 확인

- `git status`, 현재 브랜치, remotes, worktree 목록, 기존 코드·AGENTS/CLAUDE 규칙, 런타임·패키지 매니저를 확인한다.
- `CODESPACES` 등 필요한 환경 변수의 존재만 확인한다. 토큰이나 환경 변수 전체를 출력하지 않는다.
- 원격 이름은 `HeBeZ7/compiled17-hackathon`이다. 철자가 다른 이름으로 새 저장소를 만들지 않는다.
- 기존 미커밋 작업을 지우거나 임의로 한꺼번에 커밋하지 않는다. 안전하게 분리할 수 있으면 그대로 진행하고, 겹치는 수정만 사용자에게 알린다.
- 루트 AGENTS.md와 CLAUDE.md를 앱 생성기가 덮어쓰지 않게 보존한다.

### A-1. 얇지만 실행 가능한 기반

- 앱 진입점, 소개→입장→선택→교실의 화면 전환, 전역 스타일 토큰, 공통 상태, 타입, API 경계를 만든다.
- B~E 소유 영역에는 최소 인터페이스/빈 상태만 만들고, 계약 확정 후에는 해당 담당자가 구현한다.
- 공통 타입은 `src/shared/contracts/`, 공통 UI는 `src/shared/ui/`, 클라이언트 API는 `src/shared/api/`에 둔다.
- 실제 미연결 상태를 반환하는 서비스 뼈대를 만든다. UI가 연결됐다는 이유로 실제 공급자 기능이 작동하는 것처럼 응답하지 않는다.
- 설치 버전과 lockfile, 기본 검증 명령, private 개발 서버 실행 방법을 정한다. 개발 포트는 외부 공개로 자동 변경하지 않는다.
- 테스트 도구를 초기에 맞춰 F가 의존성 파일을 고칠 필요가 없게 한다. 실제 필요한 도구만 선택한다.

### A-2. 계약과 작업 공간 고정

- 아래 역할별 경로와 export/요청/응답 타입을 확정한다. 변경한 경로는 이 문서 소유권 표에도 반영한다.
- `aa/integration` 등 충돌하지 않는 통합 브랜치에 자기 기반 변경만 커밋한다. 기존 같은 이름의 브랜치가 있으면 덮어쓰지 않는다.
- 그 **하나의 기반 커밋**에서 B~F의 별도 브랜치/worktree를 만든다. 예: `aa/b-classroom`, `aa/c-onboarding`, `aa/d-learning`, `aa/e-services`, `aa/f-qa`.
- worktree는 저장소 옆의 별도 디렉터리 또는 gitignore된 내부 경로를 사용한다. 모든 작업자가 통합 checkout 안에서 같이 수정하지 않는다.
- 각 worktree의 의존성과 출력·DB·임시 파일을 분리한다. 병렬 테스트가 같은 DB나 포트를 공유하지 않게 한다. 비밀키를 추적 파일에 복사하지 않는다.
- 실제 작업 경로, 브랜치, 기반 SHA, 포트, 검증 명령, 담당 범위를 `docs/coordination/ASSIGNMENTS.md`에 적는다. 이 운영 기록은 A가 개발 착수 후 만든다.
- 기반 SHA는 그 커밋이 생긴 뒤 운영 기록에 적는다. SHA를 기록하는 커밋 자체를 기반 SHA라고 순환 참조하지 않는다. worktree 생성 후 기록 파일만 필요하면 A가 동일하게 전달한다.
- 자신이 만든 기반이 실행되는지 확인한 후 `A_READY`와 역할별 실제 경로를 사용자에게 보고한다. 이 시점은 전체 제품 완료가 아니다.

## 4. 역할과 수정 소유권

아래는 새 앱 기준의 경로다. 기존 구조가 있으면 A가 동일 책임으로 대응시킨다. 역할 간 파일을 동시에 수정하지 않는다.

## 5. 공통 계약에서 반드시 정할 것

아래 이름은 **내부 설계안**이며 외부 공급자의 실제 API 이름이 아니다. A가 export 이름과 null/오류 조건까지 고정해 작업자에게 전달한다.

| 계약 | 최소 내용 | 연결 |
| --- | --- | --- |
| ModelReference | source, publisher, modelId, revision 또는 null, licenseRef, 작업별 지원 근거 | C↔D↔E |
| AgentProfile / AvatarAsset | agentId, 이름, selectedModel, 외형 원본/렌더 참조, 입력 방식 | C→A→B/D |
| Classroom 인터페이스 | 현재 에이전트, paused/입력 잠금, 선생님 접근·상담 열기 이벤트 | B↔A↔D |
| TeacherRequest / Response | 현재 modelRef·프로필 버전·대화·사용자 목표, 응답·추천·근거·연결 상태 | D↔E의 LLM gateway |
| PriceQuote | 공급자, 지역, 통화, 단위, 단가/null, 총액 추정/null, 조회 시각, 출처, 캐시 여부, 제외 비용 | E→D |
| TrainingSpec | 기반 모델/revision, 방식, 데이터 참조, 검증된 설정, 공급자, 실행 비용 한도 | D→E |
| TrainingRun | 내부 runId, 실제 providerJobId/null, 상태, 요청 식별키, 결과물, 타임스탬프, 근거 | E→D |
| ModelArtifact / RuntimeStatus | 기반 모델 종속성, 결과물 식별, 로드 상태, 실제 응답 확인 | E→D/A |
| API 오류 | 명시적 code, 사용자가 볼 설명, 재시도 가능 여부, 필요한 설정. 비밀값 제외 | 전체 |

모델/프로필이 바뀐 뒤 이전 응답이 늦게 도착하면 최신 선택을 덮어쓰지 않는다. 서버가 학습 가능 조건을 다시 확인한다. 클라이언트 버튼 활성화만으로 지원 여부를 판단하지 않는다.

## 6. 담당자별 작업 지침

### B — 교실과 움직임

- R-009, R-016, R-018, R-019를 중심으로 교실 하나를 완성한다.
- A가 정한 미술 토큰에 맞춰 바닥·벽·책상·선생님·학습 위치·조명을 구성한다. 공간은 작아도 시각적으로 완결되어야 한다.
- 사용자 캐릭터의 실제 위치, 방향, 걷기/멈춤, 경계와 장애물 충돌을 구현한다. 동일 입력에서 대각선만 더 빨라지지 않게 한다.
- 초기 조작안은 키보드와 화면 방향패드/조이스틱이다. 텍스트 입력·모달·창 비활성화·pointer cancel/키 해제 시 이동을 정리한다.
- 선생님 근처에서 상호작용 안내를 보여주고 A의 이벤트로 상담을 연다. D의 UI를 복제하지 않는다.
- C의 사용자 그림/사진을 계약으로 받아 플레이에 반영한다. C 미완성 시 명시적 개발 자산으로 검증하고 최종 통합 때 교체한다.
- 리사이즈, 캔버스 해제, 이벤트 리스너 중복을 확인한다. 최종 플레이 화면과 이동 검증 근거를 인계한다.

### C — 모델과 캐릭터

- R-004~R-008, R-015의 사용자 선택 경로를 담당한다.
- E의 카탈로그 계약에 맞춰 검색·페이지 이동·로딩·빈 결과·실패를 처리한다. 실제 연동 전 정적 후보를 전체 모델 목록으로 표현하지 않는다.
- 실제 모델 식별자와 공급처, 확인 가능한 버전·조건·작업별 지원을 표시한다. 벤치마크가 없으면 점수 UI를 조작하지 않는다.
- 이름 입력, 직접 그리기 캔버스, 사진 선택·미리보기·반영을 구현한다. 이미지 파일 크기·형식·디코딩 실패·URL 수명을 처리한다. 첫 지원은 안전하게 디코딩 가능한 래스터 형식으로 제한할 수 있다.
- 외형은 공통 저장 계층을 통해 재진입 시 복원한다. 브라우저 파일 경로 문자열만 저장하고 성공 처리하지 않는다.
- 선택한 모델과 외형을 하나의 AgentProfile로 A에 넘긴다. 모델 준비/다운로드 상태는 E의 실제 동작을 반영한다.
- 그림과 사진 각각이 B의 교실에서 보이는지 통합 검증 조건을 남긴다.

### D — 선생님과 학습 화면

- R-011~R-014와 결과 상태 경험을 담당한다.
- 선생님의 첫 질문, 자연어 입력, 대화 맥락, 현재 선택 모델 참조, 추천 이유·근거 표시를 구현한다.
- teacher 서비스는 E의 서버 LLM gateway 계약을 사용한다. 교사 모델과 학생 모델을 별도로 기록하고 사용자의 모델 선택을 몰래 바꾸지 않는다.
- 실제 상담 연결이 없으면 고정 환영 안내와 연결 필요 상태를 구분한다. canned 응답을 실제 모델의 맞춤 상담으로 표시하지 않는다.
- 학습 자료 입력·검증 결과, 현재 모델 유지/대안 검토, 견적·비용 한도 확인, 학습 요청, 상태·오류·취소·결과물/사용 가능 여부를 연결한다.
- 공급자 데이터 형식은 E의 검증 결과를 따른다. 임의의 과목을 제품의 첫 수업으로 고정하지 않는다.
- 대화가 열리면 B의 이동을 멈추고 닫으면 복원한다. 요청 취소·모델 교체·응답 순서 뒤바뀜을 처리한다.

### E — 실제 서비스 연결

- R-004~R-006, R-013~R-015, R-002, R-017의 기술 경로를 담당한다.
- 먼저 공식 카탈로그의 읽기 연결과 모델 메타데이터를 구현한다. 접근 제한·페이지 이동·조회 실패를 처리한다.
- 공식 지원 모델·가격·현재 계정 조건을 확인하고, 최초 공급자 한 경로를 깊게 연결한다. 모든 공급자를 얕은 가짜 endpoint로 채우지 않는다.
- 관리형 파인튜닝 API와 일반 GPU VM API를 구분한다. VM 생성만 제공된다면 데이터/모델 준비, 학습 실행기, 체크포인트 저장·조회, 종료·정리까지 필요하다. VM 생성 성공을 학습 성공으로 간주하지 않는다.
- 견적·지원 확인, 모델 준비, 학습 생성·조회·취소, 결과물 확인·로드를 각각 구현·검증 수준으로 보고한다.
- 생성 요청은 지속되는 idempotency/요청 추적을 사용한다. 공급자 idempotency가 없으면 네트워크 불명 상태를 자동 재생성하지 않는다.
- 검증된 LoRA/QLoRA/전체 파라미터 학습 경로를 사용한다. prompt 수정이나 local JSON 저장으로 GPU 학습을 대체하지 않는다.
- 미확인 가격·지역·모델 지원은 null/unknown으로 반환한다. 공개 정적 가격을 실시간 재고·확정 견적으로 표현하지 않는다.
- 개발 중 live 유료 학습은 이미 승인된 모델·자료·공급자·비용 범위가 있을 때만 실행한다. 없으면 코드/대역 검증을 끝내고 정확히 부족한 조건만 인계한다.
- 비밀키·파일·데이터를 로그에 노출하지 않는다. 사용자별 자료·작업 조회 경계와 서버 입력 검증을 유지한다. 임의 URL 다운로드/실행을 허용하지 않는다.
- `docs/integrations/`에 공식 URL·확인일·지원 범위·실제 응답 유무·남은 설정을 간결히 남긴다. 키 이름은 적되 값은 기록하지 않는다.

### F — 검증과 결함 재현

- 다른 작업이 끝나기 전 PRODUCT_SPEC의 수용 기준과 A의 계약을 바탕으로 핵심 검증을 준비한다.
- 담당 경로의 테스트만 작성한다. 구현과 똑같은 코드를 베껴 참이라고 확인하는 테스트나 숫자 채우기용 테스트를 만들지 않는다.
- 이동 입력 해제/모달/텍스트 포커스/창 전환, 외형 두 경로, 모델 변경 후 상담 문맥, 가격 조회 실패, 중복 학습 방지, 취소·불명 상태, 결과 로드 실패를 우선 검증한다.
- 단위·통합 테스트의 fixture 결과와 실제 공급자 확인을 구분한다. 미설정 외부 API 때문에 전체 제품이 실제 연결됐다고 통과시키지 않는다.
- A 통합 후 실제 브라우저로 소개→선택→교실→상담을 확인한다. 데스크톱과 좁은 화면에서 글자·컨트롤·대화 패널 겹침을 본다.
- 최종 검증 대상 커밋 SHA, 명령/관찰, 재현 단계, 예상/실제 결과, 심각도, 증거 경로를 보고한다.
- 브라우저 실행이 환경 때문에 막히면 테스트 성공으로 바꾸지 말고 그 검증만 미실행으로 남긴다.

## 7. 통합 규칙

- 각 봇은 A가 지정한 기반을 공유하지만 자기 브랜치만 커밋한다. 다른 역할 결과를 임의로 합치지 않는다.
- 공통 의존성·타입 변경 요청은 역할별 인계 문서에 모은다. A는 필요한 공통 커밋을 별도로 만들고 작업자에게 적용할 정확한 SHA를 전달한다. 같은 공통 커밋을 서로 다르게 다시 작성하지 않는다.
- 각 봇은 기능 중간점에서도 작은 실행 가능한 단위를 커밋할 수 있다. 너무 큰 최종 결과만 기다리지 않는다.
- A는 인계 문서와 diff를 확인한 후 자기 통합 worktree에서 역할별 브랜치를 순차 병합한다. 이미 cherry-pick한 변경을 다시 병합하는 방식과 혼용하지 않는다.
- 소유권을 벗어난 변경이 있으면 이유를 확인하고 조정한다. `ours/theirs` 일괄 선택으로 충돌을 덮지 않는다.
- 통합 중 버그를 A가 직접 고칠 때는 해당 담당자의 같은 파일 수정이 멈췄는지 확인한다. 또는 공통 계약/진입점 안에서 해결한다.
- F의 QA worktree에 검증할 통합 커밋을 반영한다. 검증 후 제품 코드가 바뀌면 영향을 받는 검사만 다시 실행한다.
- 기본 작업은 통합 브랜치에서 한다. 기존 main 작업을 강제로 덮거나 공개 배포를 완료 처리하지 않는다.

## 8. 학습 상태 계약

초기 상태안: `draft`, `validating`, `ready`, `blocked`, `submitting`, `queued`, `running`, `cancel_requested`, `canceled`, `status_unknown`, `verifying_artifact`, `completed`, `failed`.

| 상황 | 처리 |
| --- | --- |
| 모델·자료·계정 조건 부족 | blocked와 구체적인 이유, 다른 기능은 사용 가능 |
| 생성 요청 결과 불명 | status_unknown, 기존 작업 확인. 무조건 재생성하지 않음 |
| 조회 한 번 실패 | 마지막 관측 상태와 조회 오류를 구분. 바로 학습 실패 처리하지 않음 |
| 취소 요청 접수 | cancel_requested. 공급자 확인 후 canceled |
| 취소와 완료 경합 | 공급자 실제 최종 상태를 기록. 취소 성공으로 미리 고정하지 않음 |
| 공급자 성공 응답 | verifying_artifact. 실제 결과물 확인 후 completed |
| 결과물 로드 실패 | 학습 상태와 runtime 오류를 별도로 보존. 사용 가능으로 표시하지 않음 |

`trainingCompleted`, `runtimeReady`, `evaluationResult`는 분리한다. 가중치/어댑터 결과가 있어도 아직 로드되지 않을 수 있으며, 응답이 나와도 향상이 측정된 것은 아니다.

## 9. 인계와 완료 판정

각 역할의 `docs/handoffs/<역할>.md`는 관련 R-ID, 변경 경로, 기능 커밋, 수행 검증, 실제/대역/미연결 상태, A 요청, 남은 장애를 담는다. 채팅에는 최종 커밋 SHA와 짧은 결과를 보고한다. 사용자가 그 결과를 A에게 전달한다.

A는 통합 후 `docs/coordination/STATUS.md` 하나에 다음을 수합한다. 모든 봇이 같은 상태 파일을 함께 수정하지 않는다.

| 영역 | 필수 기록 |
| --- | --- |
| 실행 | 정확한 브랜치·커밋·개발 명령·접속 포트 |
| 기능 | 수용 기준별 코드 작성 / 로컬 확인 / 공급자 확인 / 미실행 |
| 품질 | build·타입 검사·핵심 테스트·브라우저 검증 결과와 증거 |
| 실제 연동 | 실제 호출한 공급자·모델·작업 종류. 미연결은 이유 |
| 남은 일 | 막힌 경로, 필요한 환경/예산/데이터, 계속 가능한 작업 |

전체 제품 완성을 주장하려면 PRODUCT_SPEC의 해당 수용 기준을 충족해야 한다. GPU 연동이 빠진 단계라면 ‘교실·선택·상담 UI 구현’처럼 정확한 범위로 보고한다. 실패나 성능 악화도 유효한 결과이며 감추지 않는다.
